# 任務：pico-search-converter 全 repo 獨立覆審（唯讀）

**唯讀模式：禁止寫入或修改任何檔案，只輸出報告文字。**

## 專案前提（評分前必讀）

### (a) 架構限制與刻意取捨

- 純前端靜態站（Vite + React 19 + TypeScript strict），部署在 GitHub Pages。無後端、無資料庫、無網路 API 呼叫。
- `src/core`（normalize/validate/buildAst/generate）與 `src/render`（三平台 emitter）是**與 React 無關的純函式**，刻意如此以便確定性測試；UI 只在 `src/ui`。
- 範圍刻意限 **Phase 1**：只有 PubMed、Embase.com（Elsevier 介面，非 Ovid Embase）、Ovid MEDLINE 三個 target。**不做** query parser、MeSH lookup、proximity、Ovid history 格式、其他資料庫。建議新增這些功能不是有效發現。
- **刻意嚴格的字元白名單（決策 D1／D2）**：free text 僅 ASCII 字母／數字／空白／連字號；apostrophe、非 ASCII 字母一律拒絕並給改寫建議；含 and/or/not 未加引號一律拒絕。因為 vendor 的 escape 規則無官方記載，**拒絕優於輸出可能被誤解析的語法**。「太嚴格、應放行 X」只有在你能指出官方文件保證安全時才算有效發現；否則請改列為「待 live 驗證」。
- **刻意的不靜默原則**：任何 term 都不得被靜默丟棄；未勾選「已確認」的 heading 是 blocking error；輸入有錯時不保留舊輸出、停用 Copy／匯出（D9）。
- 三個平台目前皆 **Not live-validated**（`src/config.ts` 的 `LIVE_VALIDATED` 全 false）；`src/render/ovidMedline.ts` 的保留字清單是已知假設，待使用者 live 測試（`docs/live-validation.md`）。不要把「尚未 live 驗證」本身當成發現，但**若你確知某平台語法輸出錯誤**（對照官方文件），這是高價值發現。
- 測試：Vitest + jsdom + RTL，刻意不用 Playwright（D6）。T23（離線）以 `scripts/check-offline.mjs` 靜態檢查 build 產物 + 手動；T24 部分自動 + 手動。
- 測試的失效模式是**假綠燈**（斷言錨錯位置、期望值來自受測程式本身），不是測試過多。「測試可精簡／移除重複案例」不是有效發現；反之，若發現 golden 期望值是由受測程式產生、或斷言無法分辨正確與錯誤輸出，請列為高價值發現。
- 重複實作的範圍排除：測試檔、驗證器、規格明列的行為（縱深防禦，例如 core 驗證後 renderer 仍做最後防線拋錯，是刻意的）。

### (b) 威脅模型與風險權重

- 無認證、無 session、無機密、無伺服器端資料；使用者輸入只存在瀏覽器記憶體。UI 有「勿輸入病患識別資訊」提醒。
- 用途：EBM 教學與系統性文獻搜尋起稿。**最大的危害是產出「看起來正確但語意錯誤」的檢索式**，被使用者直接貼進資料庫執行，導致漏掉文獻（false negative，系統性回顧最怕的）或檢索範圍被悄悄改變（例如 Boolean 優先順序錯、括號錯、片語被拆開、heading explode 設定錯、截字被轉成別的意思、欄位標籤錯）。
- 因此嚴重度的主軸是**輸出語法正確性與是否誠實揭露限制**，高於傳統 web 安全。XSS 在此偷不到憑證，但若使用者輸入能注入語法分隔符改變檢索式結構，視為 High。
- 第二風險：複製／匯出到與目前輸入不一致的過期 query；警告文字被遺漏或被誤導（例如把 MeSH 輸出到 Embase、把 Emtree 輸出到 MEDLINE 而沒提示）。

**若某項建議與上述架構限制衝突，須明說衝突並改提相容的替代作法。**

## 輸出區塊

每項發現須含：**檔案:行號 / 嚴重度(Critical|High|Medium|Low) / 問題描述 / 建議修法**。

1. **Code review** — 邏輯錯誤、語法輸出錯誤、安全風險、例外處理不足、可維護性問題。
   其中**重複實作**須單獨列出：同一份規則／表格／轉換邏輯是否在兩處以上各寫一遍，或既有函式已提供該能力卻另起爐灶。每項須同時引用兩端 file:line，並說明兩者漂移時會產生什麼錯誤結果。範圍排除見上。
2. **Test gap analysis** — 現有測試覆蓋現況，指出未涵蓋的正常流程、邊界值、失敗情境。
3. **Dependency audit** — 過期、已知漏洞、不必要、授權有疑慮的依賴（`package.json`、`package-lock.json`）。
4. **規格符合度稽核** — 讀 `spec.md`（產品規格，含 §4 正式規則、§5 golden、§6.1 測試 T01–T25、§10 DoD），以及 `Progress.md` 的「決策紀錄」表與 `Todo.md` M0 的「已自行定案的小缺口」（**這兩處的決策覆蓋 spec 原文**，衝突時以決策紀錄為準）。逐條指出**規格宣稱有、但實作實際沒做到或做弱了**的項目。特別注意三種形態：
   - **驗證只驗了較弱的性質** —— 規格說「驗證 A 與 B 一一對應」，實作只檢查 A 的格式
   - **宣稱的欄位或功能從未產生** —— UI 有條件分支，但上游從不產生該值，功能靜默不存在
   - **宣稱的失敗處理未實際觸發** —— 錯誤分支存在但條件永遠不成立，或訊息與實際行為不符
   這不是找新需求，是查核既有承諾。每項須引用「規格條款編號（或決策紀錄列）+ 實作檔案:行號」兩端。另外，`README.md` 與 `Progress.md` 對驗證狀態的宣稱（例如測試數、T23/T24 驗證方式）若與實際不符也列入。

最後給一段總結：依嚴重度排序的前 5 項。
